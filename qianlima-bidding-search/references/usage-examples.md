# 使用案例

例子说明用户意图与调用选择，事实仍来自当次接口结果。

| 用户请求 | 执行与验收 |
| --- | --- |
| 查 500 万以上物业项目 | search 一次，一个物业组位置 [2,9]，beginAmount 5000000，不加阶段、不预检 |
| 查北京海淀区近三个月 500 万以上物业或园林招标，排除保洁 | area 提示北京暂不支持区县筛选；先问是否接受全北京市，接受后重新解析北京并 search，其他条件不变；拒绝则不查询 |
| 标题空调或新风，同时正文安装或改造 | 两个 keyword_group，位置各为 [2]、[8]；直接一次 search；位置不同的 AND 不等于跨位置 OR |
| 财政资金的空调工程，公开招标或邀请招标，没有附件 | 空调为业务组；分类 [2]、方式 [0,1]、资金 [1]、hasAnnex 0；一次 search，无附件 0 不丢失 |
| 查北京大学采购的项目／采购方是北京大学的标讯 | search，北京大学组 `[4]`；不要求产品词或公司 ID，不添加北京地区或机会阶段 |
| 查深圳市城市服务有限公司中标项目／中标单位是该公司的公告 | search，企业名 `[5]`，`infoTypes={"3":[11,12]}`；说明中标通知＋合同，不检索全量投标人 |
| 中招国际招标有限公司代理的项目／代理机构是该公司的标讯 | search，公司名 `[6]`；不混成采购方，不转 enterprise |
| 空调安装招标项目／寻找空调安装招标机会 | 空调 AND 安装，各组 `[2,9]`，机会阶段 `{"0":[3,4],"1":[2]}` |
| 空调成交结果／空调中标结果 | search，空调 `[2,9]`，结果阶段 `{"3":[11,12]}` |
| 询价采购的空调 | search，空调 `[2,9]`，方式 `[4]`；不把询价归为其他 |
| 只搜标题的空调安装，结果只有 20 条 | 两组 `[2]`，保留明确位置；给扩正文的收益和误匹配代价，不自行扩查 |
| 一般业务查询总数 80，本页 30 条，还希望更多线索 | 可给业务组加正文补查一次，保留逻辑与筛选；最终总数不相加，不逐条获取正文 |
| 标题＋标的物查到 5 条，用户只需 3 条且已满足 | 不为达到 100 条继续补查 |
| Agent 想为用户原词补充同义名称 | 先给扩词方案并等待确认，未确认不调用搜索 |
| 普通项目追问“附件与方式都不限” | 两个 null 取消条件，直接一次 refine；未改条件继承，0 不表示取消 |
| 查项目编号 ABC-2026 的采购意向 | purchase 的 keywords 为编号，matchScopes [3]；支持搜索不代表详情返回 xmNumber |
| 查联系人张先生相关临期物业项目 | expiring 支持位置 [7]；若要求物业与联系人各在独立位置，不能套用普通项目分组，保留未解决逻辑 |
| 查 9 月 1 日 09:30 起的空调公告 | 普通项目合法单端秒级 beginTime；按后一个月补齐，不要求用户再提供 endTime |
| 同查物业招标与物业采购意向 | 两个独立数据源，各用自己的时间/金额/关键词协议；各自保存 follow_up，分区展示 |
| 临期结果加 500 万以上并排除保洁 | 直接 refine，更新合同金额与用户明确的排除词、回第一页，其他条件保留 |
| 找腾讯相关公司 | search-company，名称允许简称；展示候选及注册地址，不自动分析第 1 家 |
| 查深圳市城市服务有限公司合作甲方 | 登记全称明确，直接 enterprise principals，不强制候选或外部搜索 |
| 第 1 条正文总结一下 | 当前普通项目 full-text 一次；用 content 总结，正文未采集明确说明，不先 detail |
| 第 1 条附件和来源链接 | attachments 与 detail fields sourceUrl 各一次；直接给 fileUrl；一项失败不重放成功项 |
| 已知普通公告 ID 637357877，读取附件 | `attachments --id 637357877` 一次，不补搜索，不要求名单/会话 |
| 已知采购意向/临期公告 ID，读取详情 | `detail --id ID --result-type purchase_intention` / `expiring_project`，源不明只澄清来源 |
| 换会话或 Key 后明确继续原查询 | 用原 `--result-set-id`，条件与页码准确承接；请求用当前 Key |
| 原缓存不可用，但已保存完整成功查询 | `--context-json` 复制全部 `effective_query` 与精确页码；next 加 1，refine 只改 patch 回第一页；缺项才澄清 |
| 看项目进展，再查第 2 节点联系人 | timeline 后保存新 follow_up；detail 定位时间线第 2 个节点，不误指原项目列表第 2 条 |
| 已知时间线节点公告 ID，读该节点正文 | `full-text --id ID`，不依赖原项目名单 |
| 第二、第三候选人报价多少 | 普通 detail 的 biddingCandidates；只展示实际 2/3 排名，amount null 未披露，0 保留，不补第一名 |
| 还能用多少积分，原文还能看几次 | entitlement 一次，展示 availablePoints 和 sourceUrlUsage.remaining/实际 resetAt；不估算其他调用次数 |

不能等价表达的逻辑不做近似请求；支持与未支持分支可独立时继续可用部分。详细语义样板见 [执行样板](execution-patterns.md)。
